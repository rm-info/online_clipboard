# Online Clipboard

Secure, ephemeral clipboard and file sharing between machines that cannot communicate directly.
Designed for RDP sessions where clipboard sync is disabled, or any scenario requiring
a quick, passwordless (or password-protected) data transfer between two browsers.

**v2.0.0 ships end-to-end encryption.** The server stores ciphertext only and cannot read your
messages, files, filenames, or thumbnails. There is no IP tracking — anti-abuse is proof-of-work
plus per-token quotas. Lose the password and the data is irrecoverable; the operator cannot
reset what they cannot read.

**v2.1.0 closes the served-JS gap** with three defence-in-depth additions:

- **Subresource Integrity** on every crypto script (`integrity="sha384-…"`). The browser
  refuses to execute any of the crypto bundle if its bytes drift from what the server
  intended at build time.
- **Commit hash in the About modal** linking to the GitHub commit, so users can compare
  what's deployed against the published source.
- **Installable PWA** with a service worker that pins the static crypto bundle to the
  user's local cache. Once installed, the JS the browser runs is the one the user
  accepted at install time — the per-visit "trust the server's freshly-served JS"
  window shrinks to the explicit update step.

A "private/incognito + install as app" bullet in the Privacy modal makes the optional
extra hygiene explicit.

## How it works

1. **Paste** your data on Machine A, optionally set a password, create a session
2. Your browser derives an AES-256 key from the password via Argon2id (WASM), encrypts
   everything locally, and uploads the ciphertext
3. **Share** the session URL with Machine B
4. Machine B re-derives the same key from the same password and decrypts locally
5. **Everything is wiped automatically** — no traces left after 2 hours of inactivity

Sessions can also be wiped manually at any time via the "Wipe session" button.

The UI is available in **English and French** (auto-detected from `Accept-Language`,
switchable via the language toggle in the header). A **QR-code button** next to the
session URL opens a scannable modal — handy for handing off a session from a desktop
to a phone without typing the link.

## Per-message and per-file controls

- **Secret mode** — opt-in per text item, toggled next to the message input.
  Masks both typing (`-webkit-text-security: disc`, Chromium-based browsers only)
  and the rendered card (`••••••`) with a one-click reveal. The content is still
  E2EE-encrypted like everything else; secret mode is shoulder-surfing protection,
  not additional cryptography.
- **Individual delete** — each text item and each file has a trash button.
  Removes only that entry; the rest of the session continues. Files also remove
  their on-disk ciphertext blob and any encrypted thumbnail.
- **Inline previews** — generated **in the browser** before upload and encrypted
  client-side alongside the file. The server never sees the plaintext thumb.
  - **Images**: jpg, jpeg, png, gif, webp, bmp, tif, tiff, ico — drawn to a 240px
    canvas, JPEG-encoded at 0.75 quality
  - **Text and code**: txt, md, csv, json, yaml, toml, html, css, js, ts, py, rs,
    go, sh, sql, … plus a UTF-8 + low control-char content sniff for files
    without (or with misleading) extensions. First ~16 lines drawn onto a 320×240
    canvas in monospace.
  - **PDF**: not in v2.0 — would require pulling `pdf.js` (~2 MB) into the bundle.
    On the backlog; can be added without a schema break.
  Office formats (Word / Excel / PowerPoint) intentionally not covered. Thumbnail
  fetch goes through `/{sid}/files/{id}/thumb` and returns the encrypted bytes
  for client-side decryption.
- **Header modals** — an info button opens the *About* card (app version, source
  link), and a cookie button opens the *Privacy & cookies* card detailing the
  one cookie used, where the key lives, the trust boundaries, and the retention
  window.

## Security model (v2 — E2EE)

| Layer | Mechanism |
|---|---|
| Encryption | AES-256-GCM in the browser (Web Crypto API) |
| Key derivation | Argon2id in the browser (hash-wasm) — `key = Argon2id(password, salt)` |
| Salt | 16 random bytes generated by the client at session creation, stored server-side |
| Server visibility | Ciphertext only. Filenames, thumbs, and content are all opaque to the server. |
| Transport | HTTPS only (HSTS enforced by your reverse proxy) |
| Session TTL | 2-hour sliding window, reset only on real write activity |
| Auth handshake | Client decrypts a stored verifier blob locally, sends `sha256(plaintext)` as proof |
| Anti-brute-force | Per-session failed-auth counter (`SESSION_MAX_FAILED_ATTEMPTS` → session locked forever); Argon2id makes each guess expensive |
| Anti-abuse / spam | Proof-of-work on `POST /` and `POST /{sid}/auth` (`POW_DIFFICULTY_BITS`, ~0.5s on a modern CPU); per-token write quota |
| IP tracking | None. The server logs no IPs and uses no IP-based controls. |
| Authorization cookie | `clip_token_{sid}` — HMAC-signed write token bound to the session ID. Contains no key material. |
| Key storage (client) | Raw key held in `sessionStorage` for the tab's lifetime; cleared on tab close. |
| Code delivery (v2.1) | Subresource Integrity (sha384) on every crypto script; commit hash visible + linkable in About; PWA pins the bundle to user-controlled local cache once installed. |

### Key derivation

The password never leaves the browser. Argon2id with `t=2, m=64 MiB, p=2` runs
in WASM via [hash-wasm](https://github.com/Daninet/hash-wasm). The 16-byte salt
is generated by the client at session creation and persisted server-side so a
returning visitor can rederive the same key from the same typed password.

At session creation the client also stores:

- `verifier` — AES-GCM(random 16-byte plaintext, key)
- `auth_anchor` — `sha256(verifier_plaintext)` (server-side check)

To re-authenticate, the client fetches the verifier blob, decrypts it locally,
and sends `sha256(decrypted)` as the auth proof. The server compares it to the
stored anchor; a match issues a signed write token, no key ever transits.

### Trust boundaries

What E2EE protects against:

- **The operator.** With ciphertext-only on the wire and at rest, an admin with
  shell access to the live server cannot read messages, filenames, or files.
- **Database leaks.** Redis dump and disk leak are opaque ciphertext to whoever
  reads them.
- **Brute-force at rest.** Argon2id makes each password guess expensive
  (~150 ms with the configured parameters); a strong password is intractable.

What it does **not** protect against:

- **The served JavaScript.** Any web-delivered crypto trusts the code the server
  ships. If the operator replaces `clip-crypto.js` with a malicious version,
  it could exfiltrate the password. Review the source if it matters; pin a
  commit hash and self-host if you need certainty.
- **The open tab.** Anything with code-execution access to the page — devtools,
  malicious browser extensions, malware running under the user account — can
  read the key from `sessionStorage`. Close the tab when you're done.
- **The session URL.** For password-protected sessions, the password is still
  needed to derive the key — the URL alone is not enough. For passwordless
  sessions, the URL is the only secret; share it through a trusted channel.
- **Lost passwords.** The server cannot reset what it cannot read. Forgotten
  password = data gone. Use a real password manager when it matters.

### Session IDs

- **Normal mode**: 5 characters (~916 million combinations)
- **Secure mode**: 50 characters (brute-force proof)

## Quick start

### 1. Generate your server secret

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

In v2 this secret is repurposed: it no longer peppers Argon2id (which has moved
to the browser); it's the HMAC key that signs write tokens. Same env variable,
new role.

### 2. Configure environment

```bash
cp .env.example .env
# Edit .env — paste your generated secret into CLIPBOARD_SERVER_SECRET
```

### 3. Run

```bash
docker compose up -d
```

App available at `http://localhost:8000` (bound to loopback by the default
`docker-compose.yml`). Put a reverse proxy of your choice in front for TLS —
sample Nginx config in `nginx.conf`, but Caddy, Traefik, or anything else works
as well.

---

## Production deployment

Any reverse proxy that can terminate TLS and forward to `127.0.0.1:8000` works.
The app trusts the proxy headers via FastAPI's `ProxyHeadersMiddleware` only for
scheme detection (so `secure` cookies are issued correctly); no client IP is
ever read.

### Sample: Caddy

```caddy
clipboard.your.domain {
    reverse_proxy 127.0.0.1:8000
}
```

### Build with commit hash

Pass `APP_COMMIT` to docker compose so the About modal shows the deployed commit
linked to GitHub:

```bash
export APP_COMMIT=$(git rev-parse --short HEAD)
docker compose build && docker compose up -d
```

The same value is used as the PWA service-worker cache buster (`?v=…`), so a new
deploy automatically refreshes the cached bundle on the user's next visit.

## Real-time sync

Connected browsers are updated in real time via **Server-Sent Events (SSE)**.
A three-layer approach ensures no event is ever missed:

- **SSE** — instant push on new item, wipe, lock, or expiry
- **Page Visibility API** — immediate check when a tab regains focus after being hidden
- **Polling every 30s** — fallback covering tabs that stay visible on screen while
  activity happens elsewhere (every 10s if SSE is disabled)

The SSE heartbeat (every 25s) does **not** refresh the session TTL.

---

## Session lifetime

A session lives for `SESSION_TTL_SECONDS` (2 h by default) from the last event
that the server considers a **real action**. The TTL is a sliding window applied
uniformly to all keys for a given session — text items and files in the same
session expire together.

**Refreshes the TTL:**
- Creating the session
- Adding a text item (`POST /{sid}/items`)
- Uploading a file (`POST /{sid}/upload`)

**Does NOT refresh the TTL:**
- Authenticating (`POST /{sid}/auth`) — proving you derived the right key is a
  read operation, not a write
- Loading or reloading the session page (`GET /{sid}`)
- Reading contents, downloading files, SSE stream + heartbeats, polling fallback

This means the countdown can only be extended by adding new content. Reading and
re-authentication are intentionally not enough to keep a stale session alive.

The "wipes in" countdown shown in the UI reflects the **real** Redis expiry
(passed to the page on render), not a hard-coded full TTL from page-load time.

---

## Data limits (defaults — all tunable via env)

- Max text item size: **500 KB** (plaintext)
- Max file size: **100 MiB** per file (ciphertext bytes)
- Max total file payload per session: **1 GiB**
- Global disk budget across all sessions: **10 GiB** — server-side stop before disk fills
- Per-token write quota: **240 writes / hour**
- No limit on number of text items per session
- All items are wiped after **2 hours of inactivity** or on manual wipe

When the global disk budget is reached, uploads receive `503 Service Unavailable`
with a `Retry-After` header. When the filesystem itself is out of space
(`ENOSPC`), uploads receive `507 Insufficient Storage`. Anonymous endpoints
(`POST /`, `POST /{sid}/auth`) require a valid proof-of-work; reuse or invalid
solutions return `429 Too Many Requests`.

## Operations

### `/healthz` — liveness + storage probe

Anonymous JSON endpoint suitable for an external monitor (Uptime Kuma,
healthcheck.io, k8s probes, etc.):

```json
{
  "status": "ok",
  "reasons": [],
  "redis_ok": true,
  "disk_used_bytes": 0,
  "disk_cap_bytes": 10737418240,
  "disk_ratio": 0.0,
  "warn_ratio": 0.8,
  "version": "2.1.0"
}
```

- Returns **200** when Redis is reachable and `disk_ratio < HEALTHZ_WARN_RATIO`.
- Returns **503** otherwise. The `reasons` array (`"redis_unreachable"`,
  `"disk_over_threshold"`) surfaces the failure cause directly in the response
  body.

### Disk cleanup

A background task (`CLEANUP_INTERVAL_SECONDS`, default 600 s) purges expired
session directories from disk. Redis keys expire on their own via TTL; this only
reaps filesystem leftovers so disk usage doesn't drift upward on a low-traffic
deployment.

## Upgrading from v1.x

v2.0.0 is a hard break. Sessions created on a v1.x deployment will not work
after the upgrade — the cookie names, the auth flow, and the on-disk layout all
changed. With a 2-hour TTL the impact window is small; if you want to be
careful, drain by deploying outside an active window.

For developers: the server-side `crypto.py` lost its `encrypt`/`decrypt`/
`derive_key` helpers. All crypto moved to `static/js/clip-crypto.js`. Custom
integrations that hit the JSON endpoints will need to encrypt before posting and
decrypt after fetching.
